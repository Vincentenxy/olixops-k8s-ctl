## 第 1 页：Dev Ready

建议用时：35 秒。

大家好，我今天分享的项目叫Dev Ready。它面向开发人员，提供 AI 驱动的自助开发环境。开发时，我们常常只是想要一个 Redis，或者一套临时数据库，却需要先处理镜像、存储、访问端口和环境配置。我希望开发人员能直接说出需求，由平台按照标准配置准备环境，把更多精力放在业务开发上。今天介绍的是已经具备核心流程的 PoC。

依据：README.md；docs/standard-service-quickstart.md

## 第 2 页：开发环境准备中的重复工作

建议用时：45 秒。

先看一个熟悉的场景：开发人员需要一个独立、可连接的、可快速访问验证的 Redis。为了真正用上这个环境，除了选择镜像和版本、准备配置和存储、确定访问入口并记录端口占用，还需要申请网络权限与资源，并联系运维人员进行部署。这些工作通常涉及多次沟通与等待。如果所有人共用一个实例，又容易互相影响。我们的目标，是把常用软件规格和部署流程沉淀到平台，在管理员预先配置好的网络、资源和权限边界内，让开发人员自助申请标准环境，减少重复协调。这里没有声称平台已经自动审批网络权限，也没有虚构具体节省的时间，收益需要在后续试用中量化。

依据：项目需求与 README.md

## 第 3 页：面向开发人员的自助入口

建议用时：40 秒。

这个项目的定位是开发环境自助平台。开发人员通过自己使用的 AI 客户端表达需求，平台提供标准服务目录，管理员维护规格和资源边界。现阶段，k8s-ctl 是这个平台的后端基础，提供 REST 和 MCP 两种接口。演示中我们聚焦开发环境，不把它当作生产环境发布平台，也不把当前 PoC 描述成已经完成所有治理能力的企业级 IDP。

依据：README.md；internal/interfaces/mcp/catalog.go

## 第 4 页：一次自助申请的完整流程

建议用时：50 秒。

以标准 Redis 为例，用户明确给出目标 Namespace。智能体先读取服务目录，了解支持的软件和默认规格，再调用固定的标准部署工具。平台保存配置修订、预留访问端口，检查或创建 Namespace，然后进行预检查和部署。最后需要继续查询状态并验证连接。这里有一个非常重要的区分：提交成功不代表服务已经可用。镜像拉取、存储、网关或用户网络都可能影响最终连接，所以我们把部署提交、Kubernetes 就绪和实际访问分开验证。

依据：docs/standard-service-quickstart.md；internal/application/catalog/standard.go

## 第 5 页：AI 与平台各自承担什么

建议用时：45 秒。

AI 的价值主要体现在交互和工具编排上。它把开发人员的自然语言需求转成明确的结构化参数，缺少 Namespace 时追问，再组合查询、部署和验证工具。真正的集群执行由平台处理，使用固定模板和明确的参数边界。现阶段模型运行在外部智能体客户端，控制服务本身没有内置大模型。这样既可以连接不同客户端，也可以让执行结果由集群状态和协议验证来证明，而不是依赖模型的一句“已经完成”。

依据：internal/interfaces/mcp/catalog.go；internal/application/catalog/standard.go；README.md

## 第 6 页：轻量的技术实现

建议用时：45 秒。

实现上，用户通过 AI 客户端连接 MCP 接口，普通系统也可以调用 REST API。两套接口复用同一业务层。标准服务目录用嵌入式 SQLite 保存模板、配置修订、部署记录和端口事件，不需要再部署一个数据库服务。底层通过 client-go 和受限的 kubectl、Helm 参数数组对接 Kubernetes。服务部署在集群里时，可以使用 ServiceAccount 控制所在集群。代码按领域、应用、接口和基础设施分层，后续更换客户端或扩展软件类型时，可以复用已有的部署协调流程。

依据：README.md；cmd/main.go；internal/application/catalog_cluster.go

## 第 7 页：首批标准服务目录

建议用时：40 秒。

当前代码的标准服务目录包含七类服务。Redis、PostgreSQL、MySQL、MongoDB 和 Milvus 使用持久化的单实例开发规格。Nginx 和 Python JupyterLab 沙箱使用 Deployment 和临时存储。沙箱支持到期清理。需要准确说明的是，七类模板、接口和流程已经实现，并有自动化测试覆盖，但不能据此说七种软件都在目标集群里完成过真实启动验收。镜像来源、存储和访问链路仍需要逐项验证。开发人员最终拿到的默认规格，以服务目录实际返回为准。

依据：internal/domain/catalog/software.go；docs/standard-service-quickstart.md

## 第 8 页：共享入口与端口台账

建议用时：45 秒。

当每个人都有自己的 Redis 或数据库，就需要区分访问入口。当前方案共用一个 Higress LoadBalancer，通过不同的 TCP 端口转发到不同的 Service。项目配置的端口范围是 30000 到 30200，包含两端，一共是 201 个端口。平台在分配前读取网关和所有相关路由，识别已经被其他服务占用的端口。端口与实例、部署和路由建立关联，释放时也要核对实际资源。这个数字表示配置范围，不代表当前有 201 个空闲端口，也不代表已经预先开放了全部端口。

依据：internal/application/catalog/ports.go；configs/config.yaml；docs/standard-services.md

## 第 9 页：真实案例：Redis 访问验证

建议用时：55 秒。

真实测试中，我们在 wx-test-ns-002 部署过一个 Redis，并通过共享 Higress 的 30109 端口对外提供访问。最初普通 Redis 镜像不可达，随后按要求复用了集群已有的 Opstree Redis Operator 和节点缓存镜像。Redis CR 这一步使用 kubectl 完成，并不是标准 MCP 目录已经支持 Operator。最终 Pod 就绪，持久卷绑定，客户端输入密码后得到 PONG。测试完成后，我们删除实例、回收端口，并按要求删除数据卷。这证明了当时的访问和清理结果，也提醒我们：Operator 自动化仍需要补上适配。

依据：docs/redis-operator-demo.md；对话中用户确认的 redis-cli PONG

## 第 10 页：可重试、可查询、可回收

建议用时：45 秒。

自助平台还需要处理失败。这里采用 requestId 保证相同请求重试可以恢复原流程，避免一次超时就重复创建实例。部署绑定固定的配置修订、YAML 和摘要，便于追溯。删除时核对资源 UID，先删除路由和工作负载，确认后再处理端口。数据库实例默认保留 PVC，永久删除数据需要单独操作。临时 Python 沙箱保存到期时间，由控制服务定期检查并回收。控制服务停止期间不会执行回收，重新启动后会补做，所以这里不承诺严格到秒的到期删除。

依据：internal/application/catalog/deployments.go；internal/application/catalog/standard.go

## 第 11 页：PoC 环境的风险控制与恢复

建议用时：40 秒。

PoC 的优势是可以把试错限制在专用开发环境。我们的部署要求是与生产隔离，只使用测试数据，不接入真实敏感数据，并限制操作权限和资源用量。这些要求需要管理员落实，不能仅凭“开发环境”就认为没有安全风险。应用层面，失败后复用相同 requestId 可以继续原流程，平台保留配置修订、部署记录和端口归属，确认实际路由清理后才释放端口。这能减少重复创建和资源遗留。恢复能力也有明确边界：它覆盖已有部署流程的重试和清理，不等于任意回滚、数据库数据恢复或集群故障自愈。集群崩溃、资源耗尽和数据丢失仍依赖管理员、配额以及备份恢复方案。细粒度调用者授权尚未完成，后续会继续完善。

依据：部署与恢复代码及 PoC 部署要求。

## 第 12 页：当前阶段与下一步

## 演示前准备

- 不直接重用历史实例或端口；先读实时台账。
- 确认服务版本已包含标准部署工具，优先使用已在现场集群验收的服务。
- 确认 Namespace 业务权限、镜像与存储条件。创建 Namespace 不会自动获得业务 RBAC。
- 使用新的 requestId；遇到超时复用原输入重试。
- 把客户端连接验证作为完成标志，不能只展示 applied。
- 清理数据库时先说明是否保留 PVC，永久删除数据需明确授权。
- 不在投屏、PPT 或录屏中展示真实密码、token 或 kubeconfig。

## 补充答辩

**是否已有完整 IDP 门户？** 当前交付重点是 MCP/REST 后端能力，AI 客户端承担交互，统一 Web 门户可后续建设。

**如何证明提效？** 目前没有团队级统计。试用时记录申请到首次可用的时间、人工介入次数、部署成功率、资源到期回收情况，再与原流程对比。

**是否支持生产和高可用？** 当前服务规格以单实例开发环境为主。SQLite 协调器使用单副本，尚未完成生产高可用与完整多租户治理。

**Operator 是否已经由 MCP 自动部署？** 当前历史 Redis CR 通过 kubectl 创建，MCP 参与 Namespace、通用资源和台账操作。标准目录尚未接入 Operator 的完整生命周期。

**七种软件是否都已真实验收？** 当前有模板、流程和自动化测试，不能等同于目标集群七种软件全部验收通过。

## PoC 安全与恢复的答辩口径

**是否可以完全不用担心安全和崩溃？** 专用开发环境能降低生产业务影响，前提是确实与生产隔离、不使用真实敏感数据、限制网络与资源权限。开发环境仍可能出现越权、资源耗尽或集群故障。

**已经实现哪些恢复能力？** 相同请求幂等重试、配置和部署记录追溯、按 UID 清理资源、确认实际占用后释放端口、沙箱到期清理失败后再次尝试。

**哪些恢复尚不能承诺？** 集群级灾难恢复、任意部署自动回滚、数据库备份还原和跨租户安全隔离。SQLite 及数据卷备份、资源配额和应急操作需要管理员配置，不能把恢复流程当作“永不丢数据”。
